# しくみと用語

[ドキュメント目次](README.md) ｜ 前：[チュートリアル](TUTORIAL.md)

CoToCoAを使うときに頭に置いておくとよいモデルを説明します。
ここで説明する流れが分かると、「受信したら完了通知が必要」「`MPI_COMM_WORLD` を使わない」といった
約束の理由が分かり、止まったときの原因も見当がつくようになります。

[チュートリアル](TUTORIAL.md)を一度動かしてから読むと、対応がつかみやすくなります。
用語だけ確認したい場合は、末尾の[用語集](#用語集)を見てください。

## 全体像：1つのMPIジョブの中に3種類のプロセス

CoToCoAで連携するプログラムは、**1つのMPIジョブ**としてまとめて起動されます。

```text
                 one MPI job, started by `cotocoa run`

   sender program           Coupler           receiver program
  +----------------+      +---------+        +----------------+
  | simulation     |      |         |        | analysis       |
  |   rank 0       | ---> | 1 rank  | --->   |   rank 0       |
  |   rank 1       |      |         |        |                |
  +----------------+      +---------+        +----------------+
       ranks: 2                                   ranks: 1
```

| プロセスの種類 | すること | 用意する人 |
| --- | --- | --- |
| **送信側**プログラム | 配列を作って送る | 利用者 |
| **受信側**プログラム | 配列を受け取って処理する | 利用者 |
| **Coupler** | 送信があったことを受信側へ知らせる（1プロセス） | 付属。自分では書かない |

エラーメッセージや `cotocoa` コマンドの表示では、送信側を **producer**、受信側を **consumer** と呼びます。

データは送信側から受信側へ、**一方向**に流れます。
1つのプログラムは送信側か受信側のどちらかで、両方を兼ねることはできません。
送信側・受信側のプログラムは、それぞれ複数あっても構いません。

ジョブ全体のMPIプロセス数は、全プログラムの `ranks` の合計に、Couplerの1を足した数です。

## プログラム・ポート・接続

連携の構成は、設定ファイル（YAML）に書きます。

```yaml
programs:
  simulation:
    command: ["./simulation"]
    ranks: 2
  analysis:
    command: ["./analysis"]
    ranks: 1
connections:
  - name: potential
    from: simulation.potential
    to: analysis.potential
    dtype: float64
    shape: [16, 8]
    global_shape: [32, 8]
    axes: [x, y]
```

| 用語 | 上の例では | 意味 |
| --- | --- | --- |
| **プログラム** | `simulation`、`analysis` | 連携に参加する実行単位。1つ以上のMPIプロセスで動く |
| **ポート** | `simulation.potential` の `potential` | プログラムの中での、出口・入口の名前 |
| **接続** | `connections` の1項目 | 出口のポートと入口のポートを結ぶ1本の線。流れる配列の型と形状を決める |

プログラムのコードに書くのは、**自分のプログラム名**と**自分のポート名**だけです。

```fortran
call ctx%open('simulation')                 ! 自分のプログラム名
call ctx%send('potential', field, ...)      ! 自分のポート名
```

相手が誰か、どの言語で書かれているか、何プロセスで動いているかは、コードには現れません。
そのため、設定ファイルを書き換えるだけで、相手を別のプログラムに差し替えられます。

各プログラムは、最初に自分の名前で **Context** を開き、最後に閉じます。
Contextは「CoToCoAに参加している状態」を表すもので、開いている間だけ送受信ができます。
1つのプロセスが開けるContextは1つで、開いて閉じるのは1回だけです。

## 1回の送受信で起きること

`send` を1回呼んでから、受信側の処理が終わるまでの流れです。

```text
 sender                         Coupler              receiver
 ------                         -------              --------
 send("potential", a)
  (1) copy `a` into a free
      slot of the send buffer
  (2) notice  --------------->  (3) forward  ----->  receive("potential")
  send returns;                                       (4) read the slot directly
  the sender goes on                                      from the sender's memory
  with the next step                                  (5) process the array
  (7) the slot is free  <---------------------------  (6) complete
```

1. 送信側の `send` は、配列を**送信バッファ**の空きスロットへコピーします。
2. 「配列を置いた」という通知をCouplerへ送ります。`send` はここで戻り、送信側は次の計算へ進みます。
3. Couplerは、通知を受信側へ転送します。
4. 受信側の `receive` は、通知を受け取ると、送信側のスロットから配列を直接読み取り、自分のメモリへコピーします。
   配列の本体はCouplerを通りません。
   読み取りにはMPIの片側通信を使うので、送信側と受信側が別のノードで動いていても構いません。
5. 受信側が配列を処理します。
6. 処理が終わったら、受信側は**完了通知**（`complete`）を行います。
7. 完了通知が送信側へ届くと、スロットが空きます。

この流れから、次の4つの性質が出てきます。

**送信側は、受信側の処理を待たずに先へ進めます。**
`send` が戻った時点では、受信側はまだ配列を受け取っていないかもしれません。
また、`send` は配列をコピーするので、戻った後は元の配列を自由に書き換えられます。

**完了通知を忘れると、送信側が止まります。**
スロットは、受信側が完了通知するまで空きません。
完了通知がないままだとスロットが埋まり、次の `send` が待ち続けます。

**受信側が遅いときは、送信側が待たされます。**
スロットの数は、接続ごと・送信プロセスごとに決まっています（設定の `buffer_slots`、既定は2）。
すべて埋まっているとき、`send` は最も古い送信が完了するまで待ちます。
このため、受信側が遅くても配列が失われることはありません。
代わりに、送信側の計算が受信側の速さに引きずられます。
これを避けたい場合は、[受信が追いつかないとき](DELIVERY.md)を参照してください。

**受信側が配列を読み取れるのは、送信側がMPIの処理をしている間です。**
手順4の読み取りは、送信側のプロセスがMPIの手続き（CoToCoAの呼び出しや、自分の計算のためのMPI通信）を
実行しているときに進みます。
送信側がMPIを一切呼ばずに長い計算を続けている間は、受信側は読み取りを待つことになります。
各ステップでプロセス間の通信を行う通常の並列シミュレーションでは、届くのが遅れるとしても1ステップ程度です。
遅れるだけで、配列が失われることはありません。
これはIntel MPIで確認した動作で、MPIの実装や通信方式によっては、送信側の状態に関係なく読み取れる場合もあります。

## メッセージ：配列と一緒に届く情報

受信側に届く1件分を **メッセージ** と呼びます。
メッセージには、配列のほかに次の情報が入っています。

| 情報 | 例 | 誰が決めるか | 意味 |
| --- | --- | --- | --- |
| `step` | `10` | 送信側が `send` で指定 | 計算ステップなど、利用者が付ける番号 |
| `time` | `0.5` | 送信側が `send` で指定（省略可） | 物理時刻 |
| `offset` | `[16, 0]` | 送信側が `send` で指定（省略時は0） | 全体領域の中での、この配列の開始位置 |
| `source_rank` | `1` | 自動 | 送信側プログラムの何番目のプロセスが送ったか |
| `port` | `potential` | 設定ファイル | 受信側のポート名 |
| `shape`・`global_shape` | `[16, 8]`・`[32, 8]` | 設定ファイル | この配列の形状と、全体領域の形状 |
| `axes`・`units` | `[x, y]`・`V` | 設定ファイル | 軸の名前と値の単位 |

全項目は[リファレンス](REFERENCE.md#メッセージに付く情報)にあります。

`units` などの単位は、受信側へ伝える注記です。CoToCoAが単位を換算することはありません。

## 領域分割された配列の送り方

並列計算では、1つの配列を複数のプロセスが分担して持っていることがよくあります。
CoToCoAでは、各プロセスが**自分の担当分をそのまま**送ります。

```text
   global_shape: [32, 8]

   x = 0 ........ 15   16 ........ 31
  +------------------+------------------+
  |  sender rank 0   |  sender rank 1   |   y = 0..7
  |  shape  [16, 8]  |  shape  [16, 8]  |
  |  offset [0, 0]   |  offset [16, 0]  |
  +------------------+------------------+
```

| 設定・引数 | 意味 |
| --- | --- |
| `shape`（設定ファイル） | 1プロセスが1回に送る配列の形状。全プロセスで同じ |
| `global_shape`（設定ファイル） | 全体領域の形状 |
| `offset`（`send` の引数） | その配列が全体領域のどこから始まるか。**どの言語でも0始まり** |

受信側には、各プロセスの配列が**別々のメッセージ**として届きます。
上の例で送信側が1ステップ分を送ると、受信側は2件のメッセージを受け取ります。
自動的に `[32, 8]` の1つの配列にまとめられることはありません。

受信側は、メッセージの `offset` と `source_rank` を見れば、届いた配列が全体のどの部分かが分かります。
1つの配列にまとめたい場合は、[Assembler](ASSEMBLY.md)を使います。

領域分割をしていない配列は、`shape` と `global_shape` を同じにし、`offset` を省略します。

実際のシミュレーションコードでは、次の点に注意してください。

- **袖領域（隣のプロセスと重なる部分）は送らない。**
  配列が袖領域や、隣と共有する境界の格子点を含んでいる場合は、それを除いた部分だけを送ります。
  Fortranなら `field(1:nx, 1:ny)` のような部分配列、Pythonならスライスを `send` に渡せます。
- **`shape` は全プロセスで同じにする。**
  格子数がプロセス数で割り切れないなど、プロセスによって担当分の大きさが違う分割には対応していません。
  大きさが揃う分割にするか、全プロセスが最大の大きさに合わせた配列（余った部分は使わない値で埋める）を送り、
  受信側で有効な範囲を切り出してください。後者の場合、配列どうしが重なるので[Assembler](ASSEMBLY.md)は使えません。

## 軸の順序は、どの言語でも同じ

`shape: [3, 5, 7]` の配列は、どの言語でも「第1軸が3、第2軸が5、第3軸が7」です。

| 言語 | 宣言の例 | 要素 (i, j, k) の書き方（i, j, k は0始まり） |
| --- | --- | --- |
| Fortran | `real(c_double) :: a(3,5,7)` | `a(i+1, j+1, k+1)` |
| C | `double a[3][5][7];` | `a[i][j][k]` |
| Python | `a = np.zeros((3, 5, 7))` | `a[i, j, k]` |

FortranとCではメモリ上の並び順が逆ですが、その違いはライブラリが吸収します。
Fortranで `a(2,1,1)` に入れた値は、Pythonでは `a[1,0,0]`、Cでは `a[1][0][0]` として届きます。
言語をまたぐときに、形状を逆順にしたり転置したりする必要はありません。

## 接続の種類：StreamとTask

接続には2つの種類があります。設定ファイルの `kind` で選びます。

| | **Stream**（既定） | **Task** |
| --- | --- | --- |
| 向いている用途 | 各ステップの配列を、解析や可視化へ流す | 独立した計算を、複数のワーカーへ割り振る |
| 受信側の構成 | 受信側プログラムの全プロセスが、1つの組として受け取る | 受信側プログラムを複数の組に分け、空いている組が受け取る |
| 送信の呼び出し | `send` | `submit` |
| 処理の完了を送信側で確認 | 通常はしない（`flush` や `close` でまとめて待つ） | **Ticket**で1件ごとに確認できる |

`flush` は、そのプロセスが送ったものがすべて受信側で完了通知されるまで待つ操作です。
**Ticket** は、`submit` が返す控えで、その1件が完了したかどうかを後から調べたり、完了を待ったりするのに使います。

チュートリアルで使ったのはStreamです。Taskの使い方は[計算をワーカーへ依頼する](TASKS.md)にあります。

どちらの場合も、受信側から送信側へ計算結果の配列を返すことはできません。
Ticketで分かるのは「処理が完了した」ことだけです。

## 受信側を複数プロセスで動かす

受信側プログラムの `ranks` を2以上にすると、受信側もMPI並列で動かせます。

メッセージを一緒に受け取るプロセスの組を **グループ** と呼びます。
Streamでは、受信側プログラムの全プロセスが1つのグループです。

- グループ内の**全プロセス**が、同じ順序で `receive` と `complete` を呼びます。
  1プロセスだけが受信する、という使い方はできません。
- 各プロセスには、**同じ配列**が渡されます。
  配列をプロセス間で分担して処理する場合は、`ctx.comm`（そのグループのコミュニケータ）を使って利用者が分担を決めます。
- ファイル出力など1回だけ行いたい処理は、グループ内のrank 0だけが行うようにします。

1つのグループが同時に持てる未完了のメッセージは1件です。
受け取ったメッセージを完了通知してから、次の `receive` を呼んでください。

## 終了のしかた

連携は、送信側が終わると受信側も終わる、という順で終了します。

1. 送信側は、送るものがなくなったらContextを閉じます（`close`）。
   `close` は、送った配列がすべて受信側で完了通知されるのを待ってから戻ります。
2. **すべての**送信側プログラムが閉じると、受信側の `receive` が「もう届くものはない」ことを返します。
   これを **終端** と呼びます。
3. 受信側は、終端を受け取ったらループを抜けて、Contextを閉じます。

受信側は、必ず終端まで受信を続けてください。
途中で受信をやめてContextを閉じると、エラーとしてジョブ全体が中断されます。
まだ届いていない配列を待っている送信側が、永久に待ち続けるのを防ぐためです。

同じ理由で、CoToCoAがエラーを検出した場合や、Pythonのプログラムで例外が発生した場合も、ジョブ全体を中断します。

## MPIとの関係

### 自分の計算には `ctx.comm` を使う

`MPI_COMM_WORLD` には、ジョブ内の全プロセス、つまり相手のプログラムやCouplerも含まれています。
自分のプログラムの中で `MPI_COMM_WORLD` を使って `MPI_Barrier` や `MPI_Allreduce` などを呼ぶと、
相手のプログラムやCouplerが応じないため、そこで止まってしまいます。

Contextが返すコミュニケータには、自分のプログラム（Taskの受信側では自分のグループ）のプロセスだけが入っています。
既存のMPIプログラムを組み込むときは、`MPI_COMM_WORLD` をこのコミュニケータに置き換えてください。

| 言語 | コミュニケータの取得 |
| --- | --- |
| Fortran | `ctx%comm()` |
| C | `cotocoa_comm(ctx)` |
| Python | `ctx.comm`（mpi4pyのコミュニケータ） |

### MPIの初期化と終了

Contextを開くときにMPIが初期化されていなければ、Contextが `MPI_Init` を呼び、閉じるときに `MPI_Finalize` も呼びます。
すでに自分のコード（またはmpi4py）がMPIを初期化している場合は、Contextはそれをそのまま使い、閉じるときにMPIを終了しません。
その場合の `MPI_Finalize` は、これまでどおり自分のコードで呼びます。

### スレッド

CoToCoAの呼び出し（`send`・`receive` など）は、各プロセスの1つのスレッドから行ってください。

## できないこと

| できないこと | 補足 |
| --- | --- |
| 同じプログラムが送信と受信を兼ねる、双方向・循環する連携 | データの流れは一方向。受信側から送信側へ配列を返せない |
| 実行中に変わる形状、プロセスごとに異なる分割サイズ | 型と `shape` は接続ごとに固定で、送信側の全プロセスで共通 |
| 4次元以上の配列、複素数、構造体 | `int32`・`float32`・`float64` の1〜3次元のみ |
| 単位の換算、補間、格子の変換 | 単位や軸名は注記として渡すだけ |
| Taskの計算結果を返す、依頼を取り消す、失敗した依頼を再実行する | Ticketで分かるのは処理の完了だけ |
| 一部のプロセスが落ちた後の復旧 | 復旧のしくみはない。原因を直して、新しいジョブとして実行する |

受信側から送信側の配列を読み書きしたい場合など、高水準APIで足りないときは、
[従来API](legacy/README.md)の共有領域を使う方法があります。

## 用語集

| 用語 | 意味 |
| --- | --- |
| プログラム | 連携に参加する実行単位。設定ファイルの `programs` に名前を付けて書く |
| 送信側（producer） | 配列を送るプログラム |
| 受信側（consumer） | 配列を受け取るプログラム |
| Coupler | 送信の通知を受信側へ中継する付属のプロセス。ジョブに1つ |
| ポート | プログラムの中での出口・入口の名前。`send`・`receive` に指定する |
| 接続 | 出口のポートと入口のポートを結ぶ線。設定ファイルの `connections` の1項目 |
| Context | CoToCoAに参加している状態を表すもの。最初に開き、最後に閉じる |
| メッセージ | 受信側に届く1件分。配列と、`step` などの付随情報からなる |
| 完了通知（complete） | 受信側が、メッセージの処理が終わったことを知らせる操作 |
| 送信バッファ・スロット | 送信側が、完了通知を待っている配列を置いておく場所。数は `buffer_slots` |
| 終端 | 全送信側が終了し、もう届くメッセージがないこと。`receive` が知らせる |
| グループ | メッセージを一緒に受け取る、受信側プロセスの組 |
| Stream | 接続の種類。配列を順に流す |
| Task | 接続の種類。1件ずつ、空いているグループへ割り振る |
| Ticket | 送信側が、送ったものの完了を後から確認するための控え |
| snapshot・borrow | 送信時に配列をコピーする（snapshot、既定）か、元の配列をそのまま貸す（borrow）か。[コピーせずに送る](BORROW.md) |
| all・latest | 全件を届ける（all、既定）か、新しい値を優先する（latest）か。[受信が追いつかないとき](DELIVERY.md) |
| Assembler・Frame | 分割して届いた配列を全体の配列にまとめる道具と、まとめた結果。[分割された配列をまとめる](ASSEMBLY.md) |
| 高水準API | このドキュメントが説明するAPI。`cotocoa.h`、Fortranの `cotocoa`、Pythonの `cotocoa` |
| 従来API | Requester・Coupler・Workerを自分で書くAPI。`ctca.h`、Fortranの `ctca`、Pythonの `ctca4py` |
